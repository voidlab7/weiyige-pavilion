# 门禁系统解读

> 为什么门禁分两层？协议本身在 `gates/two-layer-gate.md`，这里是设计意图。

---

## 解决的问题

AI 审查产物时容易"善意推断"——Agent 说"已完成 Lint 检查"，审查方就直接通过，不看实际证据。

## 为什么分两层

```
Layer 0（确定性检查，0 Token 成本）
    │ PASS
    ▼
Layer 1（AI 语义审查）
```

**核心思想**：能用代码检查的事情，不要让 AI 判断。

### Layer 0：确定性检查

用 `execute_command` 或 `read_file` 做硬性检查，**不通过直接打回**：

| 阶段 | 检查项 | 方法 |
|------|--------|------|
| 构思 | 方向确认文件存在 | `read_file` |
| 需求 | PRD 包含必填章节 | 关键词检查 |
| 设计 | 审查报告存在 | `read_file` |
| 开发 | Lint/类型检查通过 | `execute_command` |
| 测试 | 测试报告存在，无 Critical Bug | 关键词检查 |
| 发布 | 所有上游阶段 completed | `read_file state.json` |

**用 CLI 执行**：`weiyige-cli gate <task_id> --phase 04-development`

Layer 0 不通过 → 直接打回，**不进 Layer 1**，节省 AI token。

### Layer 1：AI 语义审查

调用 `artifact-review` Skill + 阶段门禁清单，多维度评分：

- 完整性、一致性、清晰度、范围合理性、可行性
- 各角色有专属评分维度

**评分门槛**：
- ≥40 → 通过
- 30-39 → 有条件通过
- <30 → 打回

### 审核诚实性约束

- **必须验证实际执行证据**：Agent 说"已完成"，必须看到命令输出日志
- **禁止善意推断**：没有证据 = 没有完成
- **打回必须具体**：附带文件名 + 行号 + 修改建议

## 迭代上限

| 审查类型 | 最大轮次 |
|---------|---------|
| CEO 计划审查（锋） | 3 |
| 工程审查（矩） | 3 |
| 设计审查（绘） | 3 |
| QA 测试（鉴） | 2 |
| 安全审计（盾） | 2 |

超限 → 记录到 TODOS.md，不无限循环。

## 与左移检查的关系

左移检查是"开发阶段内部的 Layer 0"——代码写完后立即跑 Lint/类型检查，不等测试阶段。

```
代码生成 → 左移检查（Layer 0）→ 通过 → 提交矩审查（Layer 1）
```
