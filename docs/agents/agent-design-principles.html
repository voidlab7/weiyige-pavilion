角色设计原则

为什么是 13 个角色？为什么这样分？

设计理念

1. 一人一职，不越界

每个角色只做 SOUL.md 中"主 Owned"的事。矩审架构不写代码，铸写代码不做架构决策。

原因：LLM 在角色模糊时容易"什么都做但什么都做不好"。明确边界 = 稳定输出。

2. 层级分离


战略层（方向）→ 执行层（拆解）→ 质量层（实现+验证）→ 运营层（持续）

不允许质量层角色做战略决策，不允许战略层角色做代码实现。

3. 制衡机制

  • 砺质疑锋的方向 → 锋可以 override 但必须记录理由
  • 矩审查铸的代码 → 铸不能跳过矩的审查
  • 鉴测试铸的实现 → 测试不过不能发布
  • 隐独立二评砺/矩的方案 → 避免单一视角

4. 最小必要原则

每个角色存在是因为有不可替代的职责：

角色不可替代性
锋唯一有最终审批权的人
砺唯一专职质疑的人（其他人倾向支持）
隐唯一做独立二评的人（避免群体思维）
枢唯一管需求拆解和进度的人
矩唯一做架构决策的人
铸唯一写代码的人（矩审方案不实现）
绘唯一管 UI/UX 的人
鉴唯一做功能测试的人
盾唯一管安全的人
算唯一管成本的人
辞唯一管内容的人
寻唯一做信息探索的人
启唯一的编排器（不干活只调度）

RACI 矩阵

决策类型R(负责)A(审批)C(咨询)I(知会)
战略方向锋用户隐、砺枢
需求定义枢锋砺矩、绘
代码实现铸矩枢鉴
UI/UX 设计绘枢矩辞
内容创作辞锋枢—
质量测试鉴枢矩盾
安全审计盾锋矩鉴
成本预算算锋枢全员
需求质疑砺用户锋枢
战略咨询隐用户锋砺

冲突解决优先级


用户决策 > 锋（CEO）最终裁决 > 砺（一票否决，仅限重大风险）> 各领域负责人
  • 砺否决后，锋可以 override，但必须记录理由
  • 技术分歧由矩裁决
  • 设计分歧由绘裁决
  • 质量分歧由鉴裁决
  • 跨领域分歧升级到锋
