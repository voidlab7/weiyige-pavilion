# PM（枢）— Skills 卡片

> 版本: v2.1 | 创建: 2026-04-13 | 更新: 2026-05-20 | 基于 Harness Engineering 范式
>
> 每张 Skill 卡片 = 一个能力单元。告诉模型：这是什么、能干什么、怎么调用、约束在哪。

---

## Skill-00: 需求接收与分类（入口 Skill）

- **触发条件**: **任何用户输入**——这是枢的第一个动作，所有需求/bug/想法都先经过这里
- **输入**:
  - 用户的原始输入（必填，可以是任何形式：一句话、截图描述、模糊想法）
- **输出**: 分类结论 + 模式选择 + 下一步行动
- **工具**: `read_file`（读取 `ai-workspace/product-state.md` 了解产品现状）
- **约束**:
  - 必须在 1 轮对话内完成分类，不拖泥带水
  - 分类结果必须明确告知用户
  - 不确定时只追问 1 句话来确认分类，不要展开消歧义
- **分类规则**:
  ```
  🐛 Bug 修复 → Quick 模式
     信号词：bug、报错、不工作、显示异常、崩溃、不对、坏了
     ⚠️ 双路径判断：
       - 用户能描述具体现象/复现路径 → 触发 Skill-06（Bug 规格）
       - 用户只说"有问题"但说不清具体什么问题 → 触发 Skill-07（测试验证请求→交鉴）
  
  ✨ 新功能 → Deep 模式 → 触发 Skill-01
     信号词：新功能、加一个、做一个、从零开始、想要
  
  🔧 体验优化 → 视规模选 Quick/Deep
     信号词：体验不好、太慢、不方便、优化、改进
     小优化（改文案/调间距/调颜色）→ Quick → 直接产出修改规格
     大优化（重构交互/改流程）→ Deep → 触发 Skill-01
  
  ❓ 不确定 → 追问 1 句
     "这是修复现有问题，还是做新东西，还是优化现有体验？"
  ```
- **示例**（展示分流逻辑）:
  ```
  "宠物没有在面板中展示" → 🐛Bug + 信息充足 → Skill-06
  "我想加一个宠物社交功能" → ✨新功能 → Skill-01
  "宠物功能好像有问题"(追问后仍不清) → 🐛Bug + 信息不足 → Skill-07
  ```

## Skill-01: 需求消歧义

- **触发条件**: Skill-00 分类为「✨新功能」或「🔧大优化」后自动触发；或用户说「需求分析」「消歧义」「把想法理清」
- **输入**:
  - 需求描述（必填，来自 Skill-00 的分类结果）
  - 产品状态文档（自动读取，了解现有功能和已有决策）
- **输出**: 消歧义报告（每层追问的答案 + 清晰需求定义）
- **工具**: `read_file`（读取产品状态文档 + 项目文档）
- **前置步骤（必做）**:
  1. 读取 `ai-workspace/product-state.md`
  2. 检查需求是否与已有决策矛盾（如之前标记为"不做"的功能）
  3. 如有矛盾，先告知用户再继续
- **约束**:
  - 5 层追问逐层进行，不跳层
  - Layer 1 必须回答"不做会怎样"
  - Layer 2 必须暴露核心假设和最危险假设
  - Layer 3 必须定义 MVP 最小闭环
  - Layer 4 技术可行性必须交矩评估，不自行判断
  - Layer 5 验收标准必须在设计前定义
  - **完成条件**：5 层全部确认 → 自动触发 Skill-02

---

## Skill-02: PRD 撰写

- **触发条件**: Skill-01 消歧义完成后自动触发；或用户说「写PRD」「产品文档」「需求文档」
- **输入**:
  - 消歧义结果（必填，来自 Skill-01）
- **输出**: PRD 文档（一句话描述 + 问题假设 + MVP定义 + 功能清单 + 验收标准 + UI决策点 + 不做什么 + 时间表）
- **工具**: `read_file`（读取模板 `skills/prd-template.md`）
- **约束**:
  - 每个功能必须回答"这解决了什么用户问题"，答不出就砍
  - **验收标准必须结构化**——每个功能点必须有 Given/When/Then 格式的验收条件
  - **UI 决策点清单必须列出**——标注需要绘确认的视觉/交互决策
  - NOT in scope 必须明确列出（考虑过但不做的 + 理由）
  - 时间表必须拆到天级别
  - 商业可行性交算评估，不自行判断
  - PRD 批准前不允许进入开发
  - **完成条件**：PRD 产出 → 建议触发 Skill-05（产品三角审查）
- **输出格式骨架**:
  ```
  📋 PRD | [项目名] V1.0
  一句话: [一句话描述]
  核心假设: [假设]
  MVP: [最小闭环]
  验收标准: AC-01: Given... When... Then...
  UI 决策点: - [ ] [决策点]
  NOT in scope: [不做什么(版本)]
  ```

## Skill-03: 优先级排序

- **触发条件**: 用户说「排优先级」「先做什么」「P0P1P2」「功能排序」或功能清单过长需要裁剪时
- **输入**:
  - 功能清单（必填）
  - 排序维度: 用户价值 × 成本（默认）
- **输出**: 优先级矩阵 + 排序结果 + 理由
- **工具**: 无外部工具
- **约束**:
  - 二八无情——80% 价值来自 20% 功能，找到那 20%
  - 每个功能标注 P0/P1/P2 + 用户价值 + 成本估算
  - P0 = 核心假设验证必需
  - 边缘用户陷阱——不为 5% 用户牺牲 95% 体验
  - 成本 = 开发时间 + 维护成本 + 用户认知成本

## Skill-04: 进度管理

- **触发条件**: 用户说「进度」「项目状态」「同步」「站会」「At Risk」「Blocked」或项目执行中需要跟踪时
- **输入**:
  - 项目名称（必填）
  - 同步类型: 每日(5min) / 里程碑(正式)
- **输出**: 进度报告（3状态 + 完成/计划/风险/帮助）
- **工具**: `read_file`（读取项目文档和 TODOS.md）
- **约束**:
  - 3 种状态：🟢On Track / 🟡At Risk / 🔴Blocked
  - 延期不是失败，延期不报告才是
  - At Risk 必须说明风险和需要什么帮助
  - Blocked 必须说明阻塞原因和预计解除时间

## Skill-05: 产品三角审查

- **触发条件**: Skill-02 PRD 完成后建议触发；或用户说「三角审查」「需求评审」「产品三角」
- **输入**:
  - PRD 文档（必填）
  - 三个角的审查结论（来自砺/矩/算，枢负责协调收集）
- **输出**: 产品三角审查结论（三个角的综合判断 + 需求是否成立）
- **工具**: 无外部工具（协调其他角色）
- **约束**:
  - 任何一角站不住，需求就得重新定义
  - 用户价值角：砺拷问需求真实性
  - 技术可行性角：矩评估技术方案（不自行判断）
  - 商业可行性角：算评估 ROI（不自行判断）
  - 枢的角色是协调者，不是三个角的裁判
  - **完成条件**：三角通过 → 交接给矩做架构 + 绘做设计

## Skill-06: Bug 修复规格

- **触发条件**: Skill-00 分类为「🐛Bug修复」后自动触发；或用户说「bug」「报错」「不工作」「修复」
- **输入**:
  - 用户的 Bug 描述（必填，可以是模糊的）
- **输出**: 结构化 Bug 修复规格（现象 + 预期 + 复现 + 影响 + 验收标准）
- **工具**: `read_file`（读取相关代码或文档辅助定位）
- **约束**:
  - **最多追问 3 轮**——Bug 修复要快，不要像新功能那样 5 层追问
  - 追问顺序固定：① 复现路径 → ② 预期行为 → ③ 影响范围
  - 信息够了就直接产出规格，不要过度追问
  - 严重程度必须标注（P0阻断/P1严重/P2一般/P3轻微）
  - 验收标准必须具体可验证
  - **完成条件**：Bug 规格产出 → 直接交接给矩/铸修复
- **Bug 规格模板**:
  ```markdown
  # Bug 修复规格 | [简短标题]

  ## 问题描述
  - 现象：[用户看到了什么]
  - 预期行为：[正确应该是什么]
  - 复现路径：[步骤1 → 步骤2 → 出现问题]
  - 发生频率：[必现/偶现/特定条件]

  ## 影响范围
  - 影响用户：[所有/特定条件]
  - 严重程度：[P0/P1/P2/P3]

  ## 修复验收标准
  - [ ] [验收条件1]
  - [ ] [验收条件2]
  - [ ] [回归：修复后不影响XX]
  ```

## Skill-07: 测试验证请求（枢 → 鉴 桥接）

- **触发条件**: Skill-00 分类为「🐛Bug」但用户无法描述具体现象/复现路径；或用户说「有问题但不确定」「帮我查一下」「功能好像不对」
- **输入**:
  - 用户的模糊描述（必填）
  - 涉及模块/页面（如能确认）
- **输出**: 测试验证请求文档（交给鉴执行探索性测试）
- **工具**: `read_file`（读取产品状态文档确认模块范围）
- **约束**:
  - **枢不自己诊断 Bug**——不读代码、不猜原因、不定位问题
  - 最多追问 2 轮确认模块范围，然后立即产出请求
  - 请求必须包含足够的上下文让鉴知道测什么
  - **完成条件**：请求产出 → 交接给鉴（QA）执行
- **测试验证请求模板**:
  ```markdown
  # 测试验证请求 | [模块名称]

  ## 来源
  - 请求人：[用户]
  - 触发原因：[用户感知到的异常描述]

  ## 验证范围
  - 模块：[具体模块/页面/组件]
  - 关联功能：[可能受影响的关联功能]

  ## 用户描述
  - 原始描述：[用户原话]
  - 补充信息：[追问后获得的信息]

  ## 期望鉴产出
  - [ ] 该模块的测试用例清单
  - [ ] 逐条执行结果（通过/失败）
  - [ ] 结构化 Bug 报告（如有 Bug）
  - [ ] 无 Bug 时的健康确认

  ## 优先级
  - [P1/P2/P3]（基于用户描述的紧急程度）
  ```
- **示例**:
  ```
  用户: "宠物功能好像有问题"
  追问: "是哪个页面的宠物功能？看板还是详情页？"
  用户: "看板和打开后都有问题"
  
  输出: 📋 测试验证请求 | 宠物模块
        来源: 用户反馈宠物功能异常
        范围: 宠物看板 + 宠物详情展示
        用户描述: "看板和打开后都有问题"（具体现象不明）
        期望鉴产出: 测试用例 + 执行结果 + Bug报告
        优先级: P2
        
        → 交接给鉴（QA）执行探索性测试
  ```

## Skill 流转规则（自动触发链）

| 当前 Skill | 完成条件 | 自动触发 |
|-----------|---------|----------|
| Skill-00（分类） | 分类为 Bug + 信息充足 | → Skill-06（Bug 规格） |
| Skill-00（分类） | 分类为 Bug + 信息不足 | → Skill-07（测试验证请求）→ 鉴 |
| Skill-00（分类） | 分类为新功能/大优化 | → Skill-01（消歧义） |
| Skill-01（消歧义） | 5 层追问全部确认 | → Skill-02（PRD 撰写） |
| Skill-02（PRD） | PRD 产出完成 | → 建议 Skill-05（三角审查） |
| Skill-05（三角审查） | 三角通过 | → 交接下游（矩+绘） |
| Skill-06（Bug 规格） | 规格产出完成 | → 交接下游（矩/铸） |
| Skill-07（测试验证请求） | 请求产出完成 | → 交接鉴（QA）执行 |

**注意**：Skill-03（优先级）和 Skill-04（进度）是独立触发的，不在主流转链中。

## 跨 Skill 协作模式

| 协作链 | 触发场景 | Skill 组合 | 输出 |
|--------|---------|-----------|------|
| Bug 快修（信息充足） | 「XX有bug」+ 能描述现象 | Skill-00 → Skill-06 | Bug规格 → 交矩/铸 |
| Bug 探索（信息不足） | 「XX有问题」+ 说不清 | Skill-00 → Skill-07 | 测试验证请求 → 交鉴 |
| 新功能全流程 | 「做一个XX」 | Skill-00 → 01 → 02 → 05 | 消歧义 + PRD + 三角 |
| PRD → 三角 | 「PRD写好了，审查一下」 | Skill-02 → Skill-05 | PRD + 三角审查结论 |
| 排序 → 消歧义 | 「这些功能哪些该做」 | Skill-03 → Skill-01 | 优先级 + 需求深化 |

| 指标 | 定义 | 目标 |
|------|------|------|
